# یادگیری از نتایج — Proposal Intelligence

این فایل **حافظه تجربی سیستم** است. هدف: Proposalهای آینده بر اساس نتایج واقعی بهتر شوند — نه حدس.

**ارتباط با فایل‌های دیگر:**
- `bids-log.md` — ثبت سریع bid ارسال‌شده (ID، مبلغ، زمان، **وضعیت**)
- `project-status.md` — **مدیریت وضعیت پروژه** (Submitted / Waiting / Negotiation / Won / Lost)
- `human-review-loop.md` — بازخورد ساخت‌یافته بعد از هر Proposal
- `negotiation-conversion-analysis.md` — **funnel مذاکره، مانع تبدیل، هدف پاسخ بعدی** (Learning — جایگزین Engine نیست)
- `proposal-generation-logic-analysis.md` — **منطق ساخت Proposal** — چرا این زاویه/قیمت/ساختار (Learning)
- `project-selection-decision-analysis.md` — **چرا این پروژه انتخاب شد** — قبل از bid + بازبینی بعد از Won/Lost
- `architecture-freeze.md` — معماری Stable؛ شرایط تغییر
- این فایل — تحلیل عمیق‌تر + یادگیری + الگو استخراج

| تریگر کاربر | عمل |
|-------------|-----|
| «پیشنهاد دادم» | ردیف در `bids-log.md` (وضعیت: **Submitted**) + **ردیف اولیه** اینجا + **`proposal-generation-logic-analysis` (بخش ۱–۳)** |
| «پاسخ داد» / «کارفرما جواب داد» | وضعیت → **Negotiation**؛ آپدیت `proposal-learning` + **`negotiation-conversion-analysis`** + **`proposal-generation-logic-analysis` (بخش ۴)** |

| «باختیم» / «انتخاب نشدم» / تشخیص Lost در پونیشا | وضعیت → **Lost** + ثبت اسکیما Lost — **بدون Lesson جدید** + **Conversion + Logic + Selection (تفکیک خطا)** |
| «رد شد» / «بی‌پاسخ ماند» | آپدیت وضعیت + تحلیل (اگر نهایی شد) |
| بررسی دوره‌ای وضعیت | اسکن پروژه‌های باز — `project-status.md` |
| بازخورد Human Review | ثبت Human Review + `[Human]` (ایراد) یا `[Human][Keep]` (تحسین) |

**بعد از هر نتیجه نهایی (برد/باخت/بی‌پاسخ):** بخش **تحلیل پس از نتیجه** اجباری است + **`negotiation-conversion-analysis`** + **`proposal-generation-logic-analysis`**.

**بعد از هر رویداد مذاکره (پاسخ کارفرما یا پاسخ ما):** **`negotiation-conversion-analysis`** — funnel، مانع، هدف پاسخ بعدی.

**بعد از هر Proposal (قبل از نهایی):** `human-review-loop.md` — چک‌لیست ۱–۵ + متن آزاد.

### Best Practice — پاسخ مذاکره (پیش‌فرض — اجباری)

**وضعیت:** فعال از ۱۴۰۵/۰۵/۱۷ — **بدون انتظار شمارنده ۵**؛ در هر پاسخ مذاکره **پیش‌فرض** رعایت شود.

**[Human][Keep] — زبان متناسب با کارفرما (مذاکره):**

از زبان و اصطلاحاتی استفاده کن که کارفرما با آن‌ها ارتباط برقرار می‌کند. سؤال مدیریتی یا تجاری → جزئیات فنی غیرضروری ممنوع — مگر کارفرما فنی باشد یا مستقیماً درباره آن سؤال کرده باشد.

**هدف:** کارفرما احساس کند پاسخ متناسب با سطح دانش و نیاز **او** است — نه نمایش دانش فنی.

| فنی (اجتناب در مذاکره مدیریتی) | معادل قابل‌فهم |
|--------------------------------|----------------|
| SSL | تنظیمات پایه امنیتی سایت |
| Permission | تنظیمات دسترسی |
| Hardening | تقویت امنیتی سایت |
| Core Update | به‌روزرسانی پایه سایت |
| Mapping | ساختار اطلاعات |
| Import | انتقال مرحله‌ای اطلاعات |
| WooCommerce setup / راه‌اندازی فنی فروشگاه | آماده‌سازی فروشگاه |
| PageSpeed / بهینه‌سازی سرعت (فنی) | بهینه‌سازی اولیه |

**جزئیات فنی مجاز فقط اگر:** کارفرما فنی باشد **یا** خودش مستقیماً درباره همان موضوع پرسیده باشد.

*(مرتبط با [Human] #17 — خلاصه عملیاتی.)*

**[Human][Keep] — تحلیل کامل تاریخچه گفتگو (مذاکره):**

قبل از نوشتن پاسخ، **کل تاریخچه گفتگو** را به ترتیب زمانی بخوان — آخرین پیام فقط یکی از ورودی‌هاست. هدف: بفهمی چه سؤال‌هایی قبلاً پاسخ داده شده، چه اطلاعات جدیدی اضافه شده، مسیر فکر کارفرما چگونه تغییر کرده. پاسخ باید **ادامه طبیعی** همان گفتگو باشد — نه پاسخ مستقل به آخرین پیام.

*(مرتبط با [Human] #18 — Negotiation Engine.)*

### [Human] — اصلاح (ادامه)

- **[Human] #6 — چک قبل از جمله اول:** «اولین جمله برای کارفرما چه احساسی ایجاد می‌کند؟» اگر فقط فنی است → بازنویسی. هدف: «مشکل من را فهمیده.»
- **[Human] #7 — زوایای متمایز brief:** اگر brief به **خلاقیت**، **موضوع/صنعت** (مثلاً سفال) یا **سئو صریح** اشاره کرد → حداقل یک اشاره. فقط migration فنی کافی نیست. *(محدودیت: #9)*
- **[Human] #8 — شروع بدون شعار:** از «فقط X نیست» خودداری کن — ارزش پروژه را **مستقیم** بگو.
- **[Human] #9 — فقط brief یا استنتاج منطقی:** فرض/سناریویی که در brief نیست نساز. فقط آنچه در brief آمده یا پیامد منطقی همان brief است.
- **[Human] #10 — اعتماد از روش، نه دفاع:** جمله‌های «در کار با فروشگاه‌ها…» کمتر — **منطق حل مسئله** تجربه را نشان دهد (mapping، نمونه، دسته‌ای).
- **[Human] #11 — خوانایی:** جمله طولانی یا چند ایده در یک جمله → **تقسیم به دو جمله کوتاه.** هدف: Scan Reading آسان — نه پاراگراف فشرده.
- **[Human] #12 — سؤال پایانی:** مهم‌ترین **ابهام** پروژه را هدف بگیر — نه سؤال فنی صرف. اول تحلیل کن کدام ابهام بیشترین تأثیر روی روش اجرا / زمان / هزینه / ریسک دارد؛ همان را بپرس. اگر سؤال دیگری ارزش بیشتری دارد، از سؤال ضعیف‌تر استفاده نکن.
- **[Human] #13 — فناوری بدیهی:** اگر stack در brief مشخص است، معرفی تکنولوژی ارزش کم دارد → **اقدام عملی** بگو (مثلاً «قبل از انتقال کامل، چند محصول نمونه منتقل می‌کنم…»).
- **[Outcome] #14 — جذب اولیه موفق:** اگر Proposal باعث شود کارفرما درباره **محدوده پروژه** سؤال بپرسد (نه سکوت یا رد)، مرحله جذب اولیه با موفقیت پشت سر گذاشته شده — **سیگنال مثبت**؛ در پاسخ بعدی scope را شفاف کن.
- **[Human] #15 — بدون تعهد ناخواسته:** هرگز از طرف کاربر تعهد جدید ایجاد نکن. اگر کارفرما درباره **پشتیبانی، گارانتی، SLA، تعداد اصلاحات، زمان پاسخ‌گویی، خدمات رایگان** پرسید → بدون تصمیم قبلی کاربر **عدد یا مدت مشخص نده**. از اطلاعات موجود استفاده کن؛ اگر کافی نیست → **پاسخ مشروط** (مثلاً «قابل انجام است؛ جزئیات را قبل از شروع با هم نهایی می‌کنیم»).
- **[Human] #16 — Scope vs شرایط همکاری:** در پاسخ مذاکره **Scope پروژه** را شفاف پاسخ بده؛ **شرایط همکاری** (پشتیبانی، گارانتی، قرارداد…) فقط در حد اطلاعات موجود — از ساختن شرایط جدید خودداری کن.
- **[Human] #17 — زبان متناسب با کارفرما:** در پاسخ مذاکره، سطح زبان را با **نوع سؤال کارفرما** هم‌راستا کن. سؤال مدیریتی → پاسخ مدیریتی (نه جزئیات فنی). هدف: کارفرما احساس کند پاسخ برای **او** نوشته شده — نه برای برنامه‌نویس. *(واژگان و Best Practice پیش‌فرض: [Human][Keep] زبان مذاکره — جدول معادل‌ها.)*
- **[Human] #18 — تاریخچه کامل گفتگو:** در پاسخ مذاکره فقط آخرین پیام را تحلیل نکن — **کل تاریخچه** را به ترتیب زمانی بخوان. بفهم: چه سؤال‌هایی قبلاً پاسخ داده شده، چه اطلاعات جدیدی اضافه شده، مسیر فکر کارفرما چگونه تغییر کرده. پاسخ = **ادامه طبیعی** گفتگو — نه پاسخ مستقل به آخرین پیام.
- **[Human] #19 — تأیید اطلاعات جدید:** اگر کارفرما بعد از سؤال اولیه اطلاعات جدید اضافه کرد → **ابتدا** همان را کوتاه تأیید کن (مثلاً «ممنون از توضیح تکمیلی» / «متوجه شدم، این ساختار مناسب‌تر است») — **سپس** ادامه پاسخ. هدف: پیام جدید واقعاً خوانده شده باشد.
- **[Human] #20 — پایان با قدم بعدی پروژه:** پایان پاسخ مذاکره بر اساس **مرحله بعدی پروژه** — نه دعوت کلی («اگر سؤال دیگری بود بفرمایید»). گفتگو را یک قدم جلو ببر (مثلاً «اگر تصاویر و اطلاعات محصولات آماده باشد، از همان ابتدا ساختار فروشگاه را بر اساس برند/مدل و نوع قطعه پیاده‌سازی می‌کنیم»). مسیر اجرا را نشان بده — بدون فشار برای بستن قرارداد.
- **[Human] #21 — Negotiation Engine ≠ مولد پاسخ:** Negotiation Engine صرفاً پاسخ نمی‌سازد — **کل فرآیند مذاکره** را مدیریت می‌کند. برای **هر پیام جدید کارفرما** Pipeline کامل اجرا شود (تحلیل → هدف پاسخ → تولید → Review → ثبت). قبل از نوشتن، تشخیص بده: **هدف این پیام چیست؟** (پاسخ به سؤال، رفع نگرانی، مذاکره Scope، مذاکره قیمت، مذاکره زمان، اعتمادسازی، بستن قرارداد، …) — سپس پاسخ را بر همان اساس تولید کن. **این قانون به Proposal Engine اضافه نشود.**
- **[Human] #22 — میانه بازه، نه تخفیف سطح ۰:** مبلغ فرم **میانه بازه بودجه** است. «کمی پایین‌تر از میانه» فقط وقتی رقابت **زیاد** است. رقابت متوسط/کم → میانه. مثال: #752921 بازه ۴۵–۱۷۰M → ۱۰۷.۵M نه ۹۰M.

### Negotiation Engine — مدیریت فرآیند مذاکره

**محدوده:** فقط بعد از ارسال Proposal — **مستقل از Proposal Engine.**

**[Human][Keep] — تفکیک دو موتور:**

| موتور | وظیفه |
|--------|--------|
| **Proposal Engine** | گرفتن **اولین پاسخ** کارفرما |
| **Negotiation Engine** | تبدیل پاسخ کارفرما به **قرارداد** |

این دو موتور **مستقل** می‌مانند — قوانین مذاکره به Proposal Engine اضافه نشود.

**نقش Negotiation Engine:** نه فقط «مولد پاسخ» — **مدیریت کل فرآیند مذاکره** از اولین پاسخ کارفرما تا بستن قرارداد (یا باخت).

| هدف پاسخ | وقتی… |

## تحلیل پس از نتیجه (اجباری)

وقتی نتیجه مشخص شد، agent این سؤالات را جواب دهد و در **تحلیل نهایی** بنویسد:

### اگر بردیم

1. کدام بخش Proposal احتمالاً تأثیرگذار بود؟ (ریسک؟ insight؟ سؤال پایانی؟)
2. قیمت/زمان نسبت به رقبا چطور بود؟
3. چه الگویی را در پیشنهادهای بعدی **تکرار** کنیم؟

### اگر باختیم یا بی‌پاسخ

1. مشکل احتمالی از کجا بود؟ (یک یا چند مورد)
   - شروع Proposal
   - اعتمادسازی
   - قیمت (زیر/بالای بازه؟ خیلی بالا/پایین؟)
   - زمان (خیلی کوتاه/بلند؟)
   - سؤال پایانی (ضعیف یا نبود؟)
   - تحلیل پروژه (سطحی بود؟)
   - ریسک (عمومی بود نه خاص پروژه؟)
   - insight (مصنوعی یا نبود؟)
   - رقابت (تعداد زیاد؟)
2. آیا کارفرما فریلنسر دیگری انتخاب کرد؟ (اگر معلوم است)
3. **Lesson Learned** — یک جمله actionable برای سیستم

#### متن Proposal واقعی ارسال‌شده

> سلام وقت بخیر
>
> هر دو ماژول را آماده دارم که برای شرکت سیراف کار کردم افتخار دادید نمونه بهتون نمایش میدم. نگران نصبش نباشید بدون ایراد براتون نصبش میکنم و اگه نخواستید بدون هیچ آسیبی حذفش می کنیم

#### Case Study — تحلیل پس از برد (نه Lesson)

**نوع ثبت:** Case Study موفق — **بدون** استخراج Lesson کلی و **بدون** Rule جدید.

##### ۱. اعتمادسازی — کدام بخش؟

| بخش متن | چرا اعتمادسازی |
|---------|----------------|
| «نمونه بهتون نمایش میدم» | پیشنهاد **اثبات ملموس** به‌جای ادعا — کارفرما می‌تواند قبل از تصمیم ببیند |
| «بدون ایراد براتون نصبش میکنم» | تعهد صریح به کیفیت تحویل — نه «سعی می‌کنم» |
| «اگه نخواستید بدون هیچ آسیبی حذفش می کنیم» | نشان می‌دهد فریلنسر از خروجی خود مطمئن است و ریسک را می‌پذیرد |

##### ۲. تجربه واقعی — کدام بخش؟

| بخش متن | چرا تجربه واقعی |
|---------|-----------------|
| «هر دو ماژول را **آماده دارم**» | محصول موجود — نه «می‌سازم از صفر» |
| «برای **شرکت سیراف** کار کردم» | مشتری واقعی از پروفایل — قابل راستی‌آزمایی |
| «هر دو ماژول» | تطابق دقیق با brief (دبیرخانه + شمسی‌سازی) — نشان می‌دهد brief خوانده شده |

##### ۳. کاهش ریسک کارفرما — کدام بخش؟

| بخش متن | ریسکی که کاهش داد |
|---------|-------------------|
| «نگران نصبش نباشید» | ترس از خراب شدن سیستم Odoo موجود هنگام نصب ماژول |
| «بدون ایراد ... نصبش میکنم» | ریسک باگ/ناسازگاری بعد از نصب |
| «بدون هیچ آسیبی حذفش می کنیم» | ریسک گیر کردن با ماژول ناخواسته — **قابلیت برگشت** |

##### ۴. تفاوت با Proposal Engine

| Proposal Engine (الگوی معمول) | Proposal واقعی #745916 |
|-------------------------------|------------------------|
| ۴–۸ جمله + رویکرد فنی + یک ریسک/Insight + ارجاع فرم + سؤال پایانی | ~۳ جمله؛ بدون جزئیات فنی، بدون ارجاع فرم، بدون سؤال پایانی |
| «می‌سازم / پیاده می‌کنم» — فرآیند آینده | «آماده دارم» — محصول موجود |
| اعتماد از طریق روش کار و تحلیل پروژه | اعتماد از طریق **نمونه زنده + مشتری نام‌برده** |
| Risk Discovery: یک ریسک مخصوص پروژه + راه‌حل | Risk Reduction: **تضمین نصب + حذف بدون آسیب** (زبان کارفرما، نه فنی) |
| Insight Engine: نکته‌ای که کارفرما ندیده | Insight ضمنی: «هر دو ماژول آماده‌اند» = زمان/هزینه کمتر از ساخت |

**جمع‌بندی Case Study:** در پروژه‌های **محصول آماده + تطابق دقیق brief + حوزه تمایز واقعی (Odoo/سیراف)**، پیام کوتاه «دارم + نمایش + نصب بی‌ریسک» ممکن است از Proposal تحلیلی Engine مؤثرتر باشد. **تکرار در بردهای بعدی لازم است** قبل از Rule.

##### قیمت/زمان نسبت به رقبا
