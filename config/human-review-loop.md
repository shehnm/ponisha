# Human Review Loop

بعد از هر Proposal — **قبل از پذیرش نهایی** — بازخورد ساخت‌یافته از صاحب سیستم گرفته می‌شود.

**هدف:** یادگیری از **سلیقه واقعی** کاربر — نه فقط نتیجه برد/باخت.

**ارتباط:** بازخوردها در `proposal-learning.md` ثبت می‌شوند. معیارهای روان‌شناسی → `emotional-trust-layer-analysis.md` (CPS + PBA + AAL + PCL).

---

## Emotional Trust Layer (قبل از Review)

**قبل از نمایش چک‌لیست Human Review:** agent **`proposal-generation-logic-analysis.md`** — **Proposal Decision Trace (Trace-۱–۵)** را در تحلیل داخلی ثبت کند.

**قبل از نوشتن بلوک ۱:** agent **`proposal-intent-control.md`** — Stage + **Attention / Trust / Response Trigger** — سپس **AAL-۱–۳**.

**بعد از پیش‌نویس، قبل از Human Review:**

- **Client Understanding Check (CUC — `proposal-engine.md`):** تست **۰** (۲ جمله اول — «فهمیده شد») + ۵ سؤال — هر «خیر» → بازنویسی **قبل** نمایش HR
- Emotional Trust (۱–۳): نگرانی انسانی، نقطه اتصال، بدون داستان‌سازی
- **Client Perspective Simulation (CPS-۱–۵):** وضعیت ذهنی، «فهمیده شدن»، تست تفاوت، اعتماد مصنوعی
- **Pattern Break Analysis (PBA-۱–۳):** First Impression (۲ جمله اول)، حذف کلیشه، نقطه مکث
- **Audience Adaptation (AAL-۴):** تأیید Language Matching و Trust Trigger در متن
- **Proposal Compression (PCL-۱–۳):** تست حذف جمله، اولویت سطح ۱–۳، قانون طول
- **Intent Control — Over-Proofing + Pre-HR Audit (Stage ۱):** توضیح زیاد؟ اطلاعات زود؟ دلیل پاسخ؟ → بازنویسی با حفظ Trust/Attention/تفاوت

اگر CPS، PBA، AAL، PCL، **CUC** (شامل تست ۰)، Pre-HR Audit یا Simulation منفی بود → **بازنویسی** بلوک ۱ — سپس Human Review.

### قانون agent — قبل از نمایش HR

**اگر متن از نظر فنی درست است ولی حس «مشکل من فهمیده شد» را در چند ثانیه اول منتقل نمی‌کند → بازنویسی کن — Human Review را نشان نده.**

این همان **تست ۰ CUC** است؛ در HR هم معیار **ارتباط انسانی** و **دید کارفرما** همین را می‌سنجند.

### قانون Human Review — بازنویسی

| وضعیت | عمل agent |
|--------|-----------|
| کاربر گفت «فنی درسته ولی فهمیده نشدم» / امتیاز پایین **ارتباط انسانی** یا **دید کارفرما** | **بازنویسی** — نه دفاع از متن فنی |
| «خوبه» بدون ایراد | نسخه نهایی — بدون Lesson |

**Proposal Engine تغییر نمی‌کند** — فقط لایه کیفیت روان‌شناسی.

## جایگاه در Pipeline

```
… → Client Simulation → امتیازدهی → بلوک ۱ + بلوک ۲ (پیش‌نویس)
    → Human Review Loop          ← اینجا
    → نسخه نهایی (یا بازنویسی)
```

**Proposal تا قبل از Review، نسخه نهایی نیست.**

agent بعد از نمایش پیشنهاد **متوقف می‌شود** و چک‌لیست زیر را نشان می‌دهد — سپس منتظر پاسخ کاربر.

## چک‌لیست — نمایش به کاربر

**سؤال کلی ممنوع:** «نظرت چیه؟» / «اوکیه؟»

**همیشه این قالب:**

---

**مرور Human Review**

Proposal را از **۱ تا ۵** ارزیابی کن (⭐ = ۱):

| بخش | امتیاز |
|-----|--------|
| شروع | ⭐⭐⭐⭐⭐ |
| اعتمادسازی | ⭐⭐⭐⭐⭐ |
| درک پروژه | ⭐⭐⭐⭐⭐ |
| لحن | ⭐⭐⭐⭐⭐ |
| سؤال پایانی | ⭐⭐⭐⭐⭐ |
| **ارتباط انسانی** | ⭐⭐⭐⭐⭐ |
| **دید کارفرما** | ⭐⭐⭐⭐⭐ |
| **شکست الگو** | ⭐⭐⭐⭐⭐ |
| **تطبیق مخاطب** | ⭐⭐⭐⭐⭐ |
| **خوانایی و قدرت پیام** | ⭐⭐⭐⭐⭐ |

**سؤال راهنما — ارتباط انسانی:**

> اگر من کارفرما بودم، در **چند ثانیه اول** آیا حس می‌کردم این فرد **مشکل من** را فهمیده — **قبل از** اینکه فقط یک متخصص فنی پاسخ داده باشد؟

**سؤال راهنما — دید کارفرما (Client Perspective Simulation):**

> آیا کارفرما بعد از خواندن Proposal احساس می‌کند این فرد **فقط دنبال گرفتن پروژه نیست**، بلکه **قبل از شروع به نتیجه فکر کرده** است؟

**سؤال راهنما — شکست الگو (Pattern Break Analysis):**

> آیا این Proposal در بین **۳۰ پیشنهاد مشابه**، دلیل کافی برای **خواندن ادامه متن** ایجاد می‌کند؟

**سؤال راهنما — تطبیق مخاطب (Audience Adaptation Layer):**

> آیا این متن **برای همین شخص** نوشته شده، یا می‌تواند برای **هر پروژه دیگری** هم ارسال شود؟

**سؤال راهنما — خوانایی و قدرت پیام (Proposal Compression Layer):**

> اگر کارفرما فقط **۱۵ ثانیه** وقت بگذارد، آیا **دلیل کافی برای ادامه خواندن** پیدا می‌کند؟

*(جزئیات: `emotional-trust-layer-analysis.md` — CPS + PBA + AAL + PCL)*

اگر ایرادی دیدی آزادانه بنویس. مثلاً:

- شروعش زیادی کلی بود
- Insight خوبی نداشت
- …

**اگر بخشی را تحسین کردی** هم بنویس (Positive Learning). مثلاً:

- سؤال پایانی عالی بود
- Insight خیلی خوب بود
- این سبک را حفظ کن

## پردازش پاسخ کاربر

### اگر فقط گفت «خوبه» / «اوکی» / «قبوله»

- **هیچ Lesson جدیدی** ثبت نشود
- در learning فقط: `Human Review: تأیید بدون اصلاح`
- Proposal **نسخه نهایی** می‌شود

### اگر بازخورد مشخص داد (ستاره یا متن)

1. امتیازها و متن را در `proposal-learning.md` → بخش **Human Review** همان پروژه ثبت کن
2. اگر ایراد **مشخص و actionable** است → Lesson با `[Human]`
3. اگر **تحسین صریح** یک بخش → ثبت با `[Human][Keep]` (Positive Learning)
4. اگر کاربر خواست اصلاح → بلوک ۱ را بازنویسی کن و **دوباره** Human Review بگیر

### Lesson از بازخورد — قالب

```markdown
- [Human] [تاریخ] [ID پروژه]: [یک جمله actionable]
  مثال: «شروع با سؤال مستقیم بهتر از جمله کلی است»
```

### Positive Learning — تحسین صریح

اگر کاربر **صراحتاً** بخشی را تحسین کرد → در `proposal-learning.md` ثبت کن:

```markdown
- [Human][Keep] YYYY-MM-DD #ID: [چه چیزی حفظ شود]
  مثال: «سؤال تخصصی پایانی — سبک تحلیل‌شده #749144»
```

**قانون:**
- «خوبه» کلی بدون اشاره به بخش خاص → **بدون** `[Keep]`
- تحسین مشخص («سؤال عالی بود»، «این سبک را حفظ کن») → `[Human][Keep]`

**Best Practice (۵ Proposal):** اگر یک ویژگی مثبت در **۵ Proposal مختلف** تکرار شد → در جدول Best Practices در `proposal-learning.md` — **الگوی ترجیحی** هنگام تولید؛ **بدون تغییر معماری**.

---

## قانون تکرار (۳ Proposal)

یک **ایراد بازخورد** وقتی در **۳ Proposal مختلف** تکرار شد:

1. در `proposal-learning.md` → جدول **بازخورد تکرارشونده** شمارنده را آپدیت کن
2. به کاربر **پیشنهاد** بده: «شاید لازم باشد `proposal-engine` یا `personal-voice` اصلاح شود»
3. **تا تأیید کاربر، معماری خودکار عوض نشود** — فقط Lesson ثبت شده

| تعداد تکرار | عمل |
|-------------|-----|
| ۱–۲ | فقط Lesson در learning |
| ≥ ۳ | پیشنهاد اصلاح Engine — طبق `architecture-freeze.md`؛ بدون تغییر خودکار |

## Architecture Freeze

معماری Stable — `architecture-freeze.md`. حتی با تکرار ≥۳، تغییر معماری فقط با شرایط Freeze یا **تأیید صریح کاربر** پس از یادآوری.

## نقشه ایراد → بخش سیستم

| بازخورد نمونه | کجا در Proposal بعدی اصلاح شود |
|---------------|--------------------------------|
| شروع کلی | قلاب — جزئیات brief |
| اعتماد کم | Risk Discovery + شفافیت |
| درک پروژه ضعیف | فاز تحلیل |
| لحن رسمی / AI | `personal-voice.md` |
| سؤال ضعیف | سؤال تخصصی پایانی |
| **ارتباط انسانی ضعیف** | `emotional-trust-layer-analysis.md` — نگرانی brief + نقطه اتصال انسانی |
| **دید کارفرما ضعیف** | CPS — تست تفاوت، فقط معرفی توانایی، اعتماد مصنوعی |
| **شکست الگو ضعیف** | PBA — ۲ جمله اول کلیشه‌ای، بدون نقطه مکث، شبیه ۳۰ bid دیگر |
| **تطبیق مخاطب ضعیف** | AAL — قالب عمومی، زبان ناهم‌خوان، Trust Trigger پوشش داده نشده |
| **خوانایی/قدرت پیام ضعیف** | PCL — طولانی بی‌دلیل، سطح ۱ ناقص |
| **Over-Proofing (Intent)** | `proposal-intent-control.md` — Stage ۱ شبیه Stage ۳؛ Scope کامل در Proposal اولیه |
| Insight نداشت | Insight Engine — یا skip درست |
| ریسک اشتباه | Risk Discovery |
| طولانی/کوتاه | ساختار بلوک ۱ |

## قبل از Proposal بعدی

agent بخش‌های زیر را از `proposal-learning.md` بخواند:

1. **Lessons از نتیجه پروژه** (برد/باخت)
2. **Lessons اصلاح** (`[Human]`)
3. **Positive Learning** (`[Human][Keep]`) و **Best Practices** (≥۵ بار)
4. **بازخورد تکرارشونده ≥۲** (ایراد) — با احتیاط بیشتر اعمال کن
