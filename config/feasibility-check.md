# ارزیابی قبل از پیشنهاد (اجباری)

کاربر پروژه‌ها را **با Cursor و مدل‌های AI** انجام می‌دهد. قبل از نوشتن پیشنهاد برای کارفرما، **اول به خود کاربر** جواب بده.

**محدوده این فایل:** Project Selection + Feasibility — **نه** Proposal Engine، **نه** Negotiation Engine، **نه** Lesson متن پیشنهاد.

**Architecture Freeze:** فقط این فایل و مستندات انتخاب پروژه — Proposal Engine / Negotiation Engine **بدون تغییر**.

---

## رتبه‌بندی انتخاب پروژه (ترتیب تصمیم)

**اول** شرایط اصلی (Fit واقعی برنده می‌شود، نه تازگی به‌تنهایی):

1. تطابق واقعی با تخصص و پروفایل shehneh
2. تجربه و نمونه‌کار واقعی + Lessons/داده برد-باخت (`bids-log`، Lost، Won)
3. امکان انجام واقعی (Cursor + AI — بخش Feasibility پایین)
4. بودجه و ارزش زمانی
5. Win Rate احتمالی
6. فعالیت کارفرما (بخش «سیگنال فعالیت کارفرما»)

**بین پروژه‌هایی که بالا را پاس کردند** — رتبه‌بندی تلفیقی:

```
Project Fit / Win Probability
    ↓
Freshness (Fresh Project Priority)
    ↓
تعداد Proposal موجود
    ↓
فعالیت کارفرما
    ↓
بودجه / ارزش زمانی
    ↓
سایر معیارهای فعلی
```

> **تازه بودن** پروژه نامرتبط یا کم‌ارزش را بالاتر از پروژه **بسیار مناسب** (مثلاً Odoo/ERP) **قرار نمی‌دهد**.

---

## ترتیب خروجی

### مرحله ۰ — فقط برای کاربر (نه پونیشا)

```
ارزیابی:
- قابل انجام با Cursor + AI: بله / بله با ریسک / خیر
- ریسک: کم / متوسط / بالا
- تناسب مهارت با پروفایل: بالا / متوسط / پایین
- احتمال برد: بالا / متوسط / پایین
- رقابت: کم / متوسط / زیاد
- بودجه: مناسب / تنگ / نامشخص
- فعالیت کارفرما: بالا / پایین / نامشخص
- Freshness: تازه / متوسط / قدیمی
- مهلت باقی‌مانده bid: …
- تعداد Proposal فعلی: …
- دلیل کوتاه (۱–۳ جمله)
```

**گزارش انتخاب (دستور «پونیشا» / «بعدی»)** — برای پروژه پیشنهادی:

```
انتخاب پروژه:
Freshness: …
مهلت باقی‌مانده: …
تعداد Proposal فعلی: …
Fit: …
دلیل اولویت: …
```

**اگر «خیر» یا «ریسک بالا»:** پیشنهاد ننویس — بگو چرا، پیشنهاد بده bid نکند یا چه شرطی لازم است. مگر کاربر بگوید «باز هم پیشنهاد بده».

**اگر فعالیت کارفرما = پایین (۷–۱۰+ روز بدون ورود/پاسخ/تعامل):** **پیشنهاد ننویس** — فقط مرحله ۰ + ثبت **Skip** در `bids-log.md`. به کاربر بگو:

> کارفرما حدود ۷–۱۰ روز به پروژه سر نزده — طبق قانون Skip می‌شود.

**استثنا:** فقط اگر کاربر صریحاً گفت «باز هم پیشنهاد بده» **یا** پروژه Odoo/ERP با Win تأییدشده مشابه دارد — با ذکر دلیل در مرحله ۰.

**اگر «بله» یا «بله با ریسک» قابل قبول:** برو مرحله ۱ — مگر Skip (فعالیت پایین، مهلت کم، یا کاربر).

### مرحله ۱ — خروجی پونیشا

فقط **متن پیشنهاد** + **فرم پونیشا** (طبق `output-format.md`).

**ممنوع در پیشنهاد کارفرما:** هر اشاره به AI، Cursor، هوش مصنوعی.

---

## Fresh Project Priority (Project Selection)

**هدف:** در پروژه‌های **مناسب**، تا حد امکان جزو **اولین** فریلنسرهای با Proposal باکیفیت باش — قبل از شلوغ شدن Inbox کارفرما.

**این یک Selection Policy است** — نه Lesson، نه Best Practice اثبات‌شده. نتایج bidهای Fresh را برای تحلیل بعدی نگه دار (`project-status.md`).

### تعریف پروژه تازه (Fresh)

بالاترین اولویت Freshness وقتی:

- به‌تازگی منتشر شده (ترجیحاً همان روز یا چند روز اخیر)
- حدود **۱۴ روز و چند ساعت یا بیشتر** از مهلت ارسال پیشنهاد باقی مانده
- **۰ Proposal** یا **تعداد بسیار کم** — رقابت جدی هنوز شکل نگرفته
- کارفرما تازه پروژه را ثبت کرده (فعالیت بالا)

**High Priority:** تازه + Fit مناسب + **۰ Proposal** → سریع وارد تحلیل Proposal شو.

### مقایسه — Fit بر Freshness

| پروژه | Fit | مهلت | Proposal | اولویت |
|--------|-----|------|----------|--------|
| A | بالا | ۱۴ روز ۲۰ ساعت | ۰ | **اول** |
| B | بالا | ۹ روز | ۱۲ | دوم |
| C | ضعیف | ۱۴ روز ۲۳ ساعت | ۰ | پایین |
| D | **بسیار بالا** (Odoo/ERP) | ۱۲ روز | ۳ | **اول** (بر C) |

### دستور «پونیشا» / «بعدی»

1. چند پروژه **مناسب** پیدا کن — **فقط اولین hit کافی نیست**
2. موارد در `bids-log` (ارسال‌شده / Skip / رد شده) را حذف کن
3. بر اساس **Fit + Freshness + Competition** مرتب کن
4. برنده را در «انتخاب پروژه» گزارش کن (قالب مرحله ۰)
5. مرحله ۰ + در صورت OK مرحله ۱

### منبع داده Freshness

- `created_at` / تاریخ انتشار در صفحه پونیشا
- مهلت bid (`bidding_closed_at` یا متن صفحه)
- تعداد پیشنهادها (`bids` / «پیشنهادها: N»)
- سن پروژه = now − created

## سیگنال فعالیت کارفرما (Project Selection)

**هدف:** پروژه‌هایی که کارفرما عملاً رها کرده را زودتر شناسایی کن — **بدون** ساخت Lesson برای متن Proposal.

### قانون — Skip اجباری (تأیید کاربر)

اگر کارفرما **۷ تا ۱۰ روز یا بیشتر** هر چهار مورد زیر را داشته باشد:

1. وارد پروژه نشده (آخرین بازدید / last seen قدیمی یا نامشخص)
2. پاسخ جدید نداده (چت پروژه یا پیام به فریلنسرها)
3. کسی را انتخاب نکرده (`status_code=3` یا متن «کارفرما این پیشنهاد را انتخاب کرده است» **نیست**)
4. تعامل قابل مشاهده ندارد (بدون سوال، بدون به‌روزرسانی brief، بدون پاسخ به پیشنهادها)

→ **فعالیت کارفرما = پایین** → **پیشنهاد ننویس** — در `bids-log.md` بخش **Skip** ثبت کن (عدم فعالیت کارفرما = **بله**).

### قانون تکمیلی — مهلت bid کم

اگر **مهلت bid کمتر از ~۲ روز** مانده **و** فعالیت کارفرما پایین است → **Skip قطعی** (حتی اگر Fit فنی خوب باشد).

### استثنا — فقط با تأیید صریح

- کاربر گفت **«باز هم پیشنهاد بده»**
- **یا** Odoo / ERP / ماژول سازمانی با Win تأییدشده مشابه (تجربه سیراف)

در استثنا در مرحله ۰ بنویس: **«با وجود فعالیت پایین کارفرما، به‌خاطر [دلیل] ادامه می‌دهیم.»**

### منبع داده

- صفحه پروژه پونیشا (تاریخ عضویت کارفرما، آخرین فعالیت، تعداد پیشنهادها)
- چت / گفتگوی پروژه
- `config/bids-log.md` — بخش Skip

### ثبت Skip

اگر کاربر Skip کرد یا agent توصیه Skip داد و کاربر تأیید کرد:

- در `config/bids-log.md` → بخش **Skip**
- اگر دلیل اصلی عدم فعالیت کارفرما بود → ستون **عدم فعالیت کارفرما = بله**
- **لینک مستقیم پروژه** حتماً ثبت شود: `https://ponisha.ir/project/{ID}`

گزارش دوره‌ای: `config/project-status.md`

## ریسک بالا — معمولاً پیشنهاد نده

- **نرم‌افزار حسابداری / مالی / فاکتور و گزارش مالی** — فعلاً خارج از توان کاربر (تا اطلاع بعدی)
- طراحی **فقط** دستی Figma بدون پیاده‌سازی وب (کارفرما Figma خالص می‌خواهد)
- اپ **نیتیو** iOS/Android بدون تجربه قبلی
- بازی، Unity، سرور گیم (SAMP و …)
- سخت‌افزار، PLC، embedded
- بودجه/زمان غیرواقعی برای scope (مثلاً GTmetrix 98 + گرافیک کامل + ۲۰ صفحه در ۵M)
- پروژه‌ای که **حضور فیزیکی** یا تیم بزرگ می‌خواهد
- nopCommerce عمیق بدون دسترسی تست و scope مبهم

---

## ریسک متوسط — با شرط پیشنهاد بده

- Figma + وردپرس: UI از HTML/import، نه طراحی دستی خالص
- فروشگاه کامل با امکانات زیاد در بودجه تنگ -> زمان و قیمت واقع‌بینانه در فرم
- nopCommerce: فقط با لینک سایت + لیست تفاوت‌ها + دسترسی
- scope مبهم: قیمت اولیه + «بعد از جزئیات تنظیم می‌کنم»

---

## چک‌لیست سریع

1. stack پروژه در توان کاربر + AI هست؟
2. بودجه و زمان با scope می‌خواند؟
3. کارفرما چیز غیرقابل انجام با AI می‌خواهد؟ (Figma دستی خالص، native app، …)
4. سطح ۰ پونیشا + رقابت زیاد -> ریسک acceptance
5. **فعالیت کارفرما** — ۷–۱۰+ روز بدون ورود/پاسخ/انتخاب/تعامل → **Skip** (پیشنهاد ننویس)
6. **مهلت bid** — کمتر از ~۲ روز + فعالیت پایین کارفرما → **Skip قطعی**
7. **Freshness** — بین Fitهای مشابه، تازه‌تر + Proposal کمتر اول (`Fresh Project Priority`)

هر «نه» جدی -> ارزیابی منفی یا Skip. فعالیت پایین = **بدون پیشنهاد** مگر استثنای صریح کاربر.
