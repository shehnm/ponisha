## ۲. استخراج داده (تحلیل)

### ۲.۱ نوع پروژه

| بعد | مقدار |
|-----|--------|
| دسته اصلی | **Debug / Troubleshooting** |
| زیردسته | رفع اشکال افزونه وردپرس |
| ماهیت کار | تشخیص ریشه خطا + رفع تداخل — نه توسعه feature جدید |
| پیچیدگی واقعی | **بالا** (برخلاف ظاهر brief کوتاه) |

**شرح:** کارفرما به‌دنبال رفع Fatal error و رفتار نادرست افزونه «پیام یار» بود. brief نشان می‌داد مشکل از قبل توسط فریلنسر دیگر و پشتیبان افزونه بررسی شده — یعنی scope واقعی **عمیق‌تر از یک fix ساده** بود.

### ۲.۲ مهارت‌های مورد استفاده

| مهارت | سطح استفاده | شواهد |
|-------|-------------|--------|
| WordPress / PHP | اصلی | افزونه، mu-plugin، hookها |
| Debug / Error tracing | اصلی | Fatal error، loop در `get_terms` |
| Plugin conflict analysis | اصلی | تداخل افزونه‌ها / must-use plugin |
| Systematic troubleshooting | اصلی | رد کردن fixهای سطحی که قبلاً شکست خورده |
| ارتباط فنی با کارفرما | فرعی | توضیح ریشه مشکل به کارفرمای خسته از تلاش‌های قبلی |

**Stack:** WordPress، PHP — در محدوده `feasibility-check.md` (تأییدشده).

### ۲.۳ الگوی اعتماد کارفرما

| مرحله | رفتار کارفرما | معنی |
|-------|---------------|------|
| قبل از bid | فریلنسر قبلی + پشتیبان افزونه درگیر شده | **اعتماد پایین** به راه‌حل‌های سطحی |
| هنگام انتخاب | انتخاب فریلنسری که **ریشه** را فهمیده | **اعتماد بر اساس شایستگی فنی** — نه قیمت پایین |
| بعد از Won | پرداخت ۵.۹M (بالاتر از بازه صفحه) | پذیرش **ارزش واقعی scope** |

**الگوی اعتماد (`trust-pattern`):**

```
کارفرمای خسته از شکست → به‌دنبال تشخیص ریشه → پرداخت برای حل واقعی
```

**نشانه‌های قابل تشخیص در brief مشابه:**
- اشاره به تلاش‌های ناموفق قبلی
- خطای Fatal / crash / loop
- درگیری پشتیبان رسمی افزونه یا توسعه‌دهنده
- بودجه اولیه **کم** در برابر شرح **پیچیده**

### ۲.۴ دلیل احتمالی برد

| عامل | وزن | توضیح |
|------|-----|--------|
| تشخیص فنی ریشه مشکل | **بالا** | تفاوت با fixهای سطحی که قبلاً شکست خورده |
| تجربه debug افزونه WP | **بالا** | mu-plugin، تداخل، tracing خطا |
| تطابق scope با توان واقعی | **متوسط** | brief کوتاه ولی کار عمیق — bid منعکس‌کننده scope واقعی |
| قیمت منصفانه برای ارزش | **متوسط** | ۵.۹M برای debug عمیق — کارفرما scope را پذیرفت |
| سرعت تحویل | **پایین** | ۲۵ روز — اولویت اصلی «حل شدن» بود نه ۱ روز |

**فرضیه برد (برچسب احتمالی):**

> برنده کسی بود که در پیشنهاد/مکالمه نشان داد **مشکل از کجاست** (تداخل / mu-plugin / loop) — نه فقط «من هم امتحان می‌کنم».

**متن پیشنهاد:** در API/ریپو موجود نیست — تحلیل از brief + outcome + تأیید نویسنده.

### ۲.۵ نکته قابل استفاده برای Proposal Engine

> **یادداشت تحلیلی** — نه قانون جدید. Proposal Engine تغییر نمی‌کند.

| # | نکته | کاربرد در bid آینده |
|---|------|---------------------|
| 1 | **بودجه صفحه ≠ ارزش واقعی** در debug | اگر brief پیچیده ولی بازه پایین است → قیمت بر اساس **scope واقعی**، نه سقف صفحه |
| 2 | **Brief «رفع اشکال» با سابقه شکست = فرصت** | کارفرمای خسته تمایل به پرداخت بیشتر برای **قطعی‌ترین** راه‌حل دارد |
| 3 | **در پیشنهاد: رویکرد تشخیصی** | به‌جای «انجام می‌دهم» → «اول X را چک می‌کنم (mu-plugin / conflict / …)» |
| 4 | **زمان ۲۰–۲۵ روز برای debug عمیق** | هم‌خوان با این Won — عجله ۱–۳ روزه برای این نوع مناسب نیست |
| 5 | **Feasibility: OK** | در stack تأییدشده WP/PHP — ریسک policy پایین |

**سیگنال‌های match برای پروژه مشابه:**

- [ ] وردپرس + افزونه + خطای Fatal/crash
- [ ] سابقه تلاش ناموفق فریلنسر/پشتیبان
- [ ] بودجه اولیه پایین + شرح فنی طولانی
- [ ] کارفرما به «ریشه مشکل» اشاره کرده

**سیگنال‌های red flag (همان پروژه):**

- [ ] بدون دسترسی staging/log
- [ ] کارفرما غیرفعال (مثل #747917)
- [ ] scope نامشخص «هر مشکلی را حل کن» بدون دسترسی
