# موتور پیشنهاد — Win Rate First

**هدف سیستم:** افزایش نرخ برنده شدن پروژه (Win Rate) — نه تولید متن زیبا.

اگر پیشنهاد خوش‌فرم باشد ولی احتمال انتخاب را بالا نبرد، **شکست** است.

این فایل موتور تولید **بلوک ۱ (متن پیشنهاد)** را تعریف می‌کند.
قوانین بودجه، مرحله‌بندی، bids-log، feasibility و output-format **حفظ شده‌اند** — فقط نحوه نوشتن متن چت عوض شده.

---

## ترتیب اجرا (یکپارچه با AGENTS.md)

```
۰. feasibility-check.md     → آیا اصلاً bid بزنیم؟
۰.۵ این فایل — تحلیل پروژه  → فقط برای agent (نه خروجی کارفرما)
۰.۷ نقش کارفرما + امتیازدهی → حداقل ۹۰/۱۰۰ در هر ۸ معیار
۱. output-format.md         → بلوک ۱ + بلوک ۲
```

---

## فاز تحلیل (اجباری — فقط برای agent)

قبل از نوشتن یک کلمه پیشنهاد، این بخش را پر کن (در خروجی ننویس مگر کاربر بخواهد):

| محور | سؤال |
|------|------|
| هدف واقعی | کارفرما با این پروژه دقیقاً چه نتیجه‌ای می‌خواهد؟ (فروش؟ اعتماد؟ سرعت؟ رفع درد فوری؟) |
| نگرانی پنهان | از چه چیزی می‌ترسد؟ (تأخیر، خراب شدن سایت زنده، هزینه اضافه، فریلنسر غایب، کیفیت پایین) |
| تجربه بد قبلی | احتمالاً قبلاً با چه چیزی اذیت شده؟ (قالب آماده، وعده توخالی، بدون پشتیبانی، قیمت پنهان) |
| ریسک فنی | مهم‌ترین ریسک فنی این پروژه چیست؟ |
| ریسک زمانی | چه چیزی می‌تواند timeline را بکشد؟ |
| ریسک مالی | scope creep یا ابهام کجاست؟ |
| پیچیده‌ترین بخش | سخت‌ترین قسمت کار کدام است؟ |
| ابهامات | چه چیزهایی هنوز مشخص نیست و باید در پیشنهاد یا سؤال پایانی اشاره شود؟ |

**منبع داده:** brief پروژه + `profile.md` + `bids-log` + رقابت.

---

## اصول ۱۱گانه (خلاصه)

| # | اصل |
|---|-----|
| ۱ | ساختار ثابت، احساس template نده — هر پیشنهاد از brief شروع شود نه از جمله ثابت |
| ۲ | تحلیل بالا اجباری است |
| ۳ | نقش کارفرما: «با دیدن این پیشنهاد اعتماد می‌کنم؟» — اگر نه، بازنویسی |
| ۴ | صدای توسعه‌دهنده باتجربه — نه فروشنده، نه بازاریاب، نه ChatGPT |
| ۵ | اعتماد از درک پروژه + ریسک واقعی + راه‌حل کوتاه + شفافیت — نه از ادعای «حرفه‌ای/کیفیت بالا» |
| ۶ | **هیچ تجربه‌ای اختراع نشود** — فقط `profile.md` و سوابق واقعی |
| ۷ | تجربه مرتبط طبیعی بیاید («در پروژه‌های ERP…») نه رزومه |
| ۸ | ارزش اضافه: یک بینش که کارفرما شاید ندیده باشد |
| ۹ | پایان با **سؤال تخصصی** — نه «اگر سؤال داشتید» |
| ۱۰ | امتیازدهی خودکار قبل از تحویل (جدول پایین) |
| ۱۱ | بودجه، مرحله، bids-log، feasibility، output-format **بدون حذف** |

## ممنوع — جملات اعتمادسازی کلیشه‌ای

این‌ها **هرگز** در بلوک ۱ نیایند:

- من حرفه‌ای هستم / سال‌ها تجربه دارم
- کیفیت بالا / بهترین قیمت
- در خدمت شما / خوشحال می‌شوم / لطفاً توجه فرمایید
- تضمین ۱۰۰٪ / بی‌نقص / متعهد به کیفیت
- هر وعده بدون پشتوانه فنی

## ممنوع — عبارات تکراری (ضد template)

این‌ها در پیشنهادهای متوالی **تکرار نشوند**:

- «چند پروژه مشابه» / «چند فروشگاه زدم» بدون جزئیات فنی
- «توی brief ندیدم» / «توی توضیحات مشخص نیست» — حداکثر یک بار؛ جایگزین: «مشخص نیست …»، «این بخش رو باز نکردید»، یا مستقیم سؤال
- «سلام وقت بخیر» در **همه** پیشنهادها — اختیاری؛ بعضی پروژه‌ها مستقیم شروع بهترند

---

## مجاز — ساخت اعتماد (Consultative + Risk Reduction)

- یک جمله که نشان دهد brief **واقعاً** خوانده شده (جزئیات خاص پروژه، نه عنوان کلی)
- **یک ریسک واقعی** + **یک جمله راه‌حل** (مثلاً: «اگه محصولات زیاد باشه، import اولیه طول می‌کشه — قبل از شروع تعداد و فرمت فایل رو چک می‌کنم»)
- روش کار شفاف و کوتاه (ابزار واقعی از پروفایل)
- اگر scope مبهم: قیمت اولیه در فرم + «بعد از لیست دقیق تنظیم می‌کنم» (بدون عدد در متن)
- تجربه واقعی فقط وقتی **مرتبط** است

---

## ساختار بلوک ۱ — انعطاف‌پذیر (نه قالب ثابت)

**ترتیب ثابت نیست.** هر پیشنهاد ۴–۸ جمله کوتاه (حداکثر ~۱۲ خط). معمولاً شامل:

1. **قلاب شخصی** — اشاره به جزئیات خاص brief (نه همیشه «سلام وقت بخیر»)
2. **درک مسئله** — هدف یا نگرانی کارفرما را نشان بده
3. **رویکرد فنی** — چه می‌کنی، با چه ابزار (از پروفایل)
4. **ریسک + کاهش ریسک** — یک مورد واقعی
5. **بینش / ارزش اضافه** — یک نکته که کارفرما شاید ندیده باشد
6. **ارجاع به فرم** — «مبلغ و زمان رو در بخش پیشنهاد ثبت کردم»
7. **سؤال تخصصی پایانی** — باز کردن گفتگو

**ممنوع در بلوک ۱:** عدد قیمت، عدد زمان، جدول markdown، بولت زیاد، AI/Cursor.

---

## نقش کارفرما (اجباری قبل از تحویل)

agent این سؤالات را از خودش بپرسد:

1. آیا فکر می‌کنم این نفر brief من را خوانده؟
2. آیا یک ریسک واقعی را دیده که خودم نگرانش بودم؟
3. آیا شبیه ۵۰ پیشنهاد دیگر نیست؟
4. آیا حاضرم همین الان یک سؤال جواب بدهم؟
5. آیا جایی احساس فروش اجباری می‌کنم؟

اگر هر پاسخ منفی است → بازنویسی.

---

## امتیازدهی خودکار (اجباری — حداقل ۹۰/۱۰۰ هر کدام)

قبل از تحویل، agent در ذهن (یا در گزارش داخلی) امتیاز دهد:

| معیار | سؤال کنترل کیفیت |
|--------|------------------|
| اعتماد | ریسک واقعی + شفافیت بدون لاف؟ |
| طبیعی بودن | مثل پیام انسان می‌خواند؟ |
| شخصی بودن | فقط برای این پروژه نوشته شده؟ |
| عدم کلیشه | هیچ جمله آماده تکراری نیست؟ |
| عدم شباهت AI | ریتم و لحن یکنواخت رباتیک ندارد؟ |
| ارزش فنی | کارفرما یک نکته فنی یاد می‌گیرد؟ |
| وضوح | بدون ابهام در روش کار؟ |
| احتمال پاسخ | سؤال پایانی دعوت به گفتگوست؟ |

**اگر هر معیار < ۹۰:** بازنویسی بلوک ۱ (نه کل سیستم).

---

## تنوع باز کردن پیشنهاد (ضد template)

هر پیشنهاد **یکی** از این سبک‌های شروع را انتخاب کند (بر اساس پروژه — نه تصادفی):

- مستقیم روی جزئیات brief
- اشاره به نگرانی محتمل («معمولاً توی چنین پروژه‌هایی…»)
- سؤال کوتاه embedded در جمله اول
- اشاره به محدودیت فنی مشخص پروژه

**هرگز** دو پیشنهاد پشت‌سرهم با همان ساختار جمله‌به‌جمله شروع نشوند.

**پشتیبانی رایگان** (مثلاً ۷ روز) فقط اگر در الگوی فنی `MEMORY.md` یا brief پروژه باشد — وگرنه ذکر نکن.

## ارتباط با رقابت (Win Rate)

از `competition-guide.md`:

- رقابت زیاد → تمایز با **درک پروژه** و **ریسک** — نه ارزان‌ترین قیمت
