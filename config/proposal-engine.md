# موتور پیشنهاد — Proposal Intelligence Engine

**هدف:** افزایش Win Rate + **یادگیری مستمر** از نتایج واقعی.

این فایل موتور **بلوک ۱** را تعریف می‌کند.
قوانین بودجه، مرحله‌بندی، bids-log، feasibility، output-format، pricing، milestones، profile، competition — **بدون حذف**.

**فایل‌های مکمل:**
- `personal-voice.md` — شخصیت نوشتاری
- `proposal-learning.md` — یادگیری از برد/باخت + Human Review
- `human-review-loop.md` — بازخورد ساخت‌یافته قبل از نسخه نهایی

## Risk Discovery Engine

**قبل از نوشتن،** ریسک‌های **مختص همین پروژه** را لیست کن (داخلی — همه را در Proposal ننویس).

### نقشه ریسک بر اساس نوع پروژه

| نوع | ریسک‌های محتمل (کشف کن، کپی نکن) |
|-----|----------------------------------|
| فروشگاه / ووکامرس | ساختار دسته‌بندی، import محصول، درگاه پرداخت، موجودی، سرعت با محصول زیاد |
| ERP / Odoo | مهاجرت داده، workflow موجود، آموزش کاربر، یکپارچگی |
| وردپرس / امنیت | منبع آلودگی، افزونه کرک، reinfection، بکاپ ناقص |
| وردپرس / عمومی | قالب سنگین، افزونه conflict، کش، هاست |
| API / اتوماسیون | سازگاری نسخه، webhook تأخیر، idempotency، rate limit |
| UI / Elementor | موبایل، سرعت، SEO حین redesign، محتوا ناقص |
| پایتون / ربات | پرداخت تکراری، state اشتراک، تحویل محتوا |
| دو زبانه | ترجمه، RTL/LTR، SEO هر زبان |

### قواعد

1. از brief **استخراج** کن — نه لیست عمومی
2. حداقل ۲ ریسک مخصوص پروژه شناسایی کن
3. **فقط مهم‌ترین یکی** (+ یک جمله راه‌حل) در بلوک ۱ بیاید
4. ریسک عمومی مثل «ممکن است تأخیر داشته باشیم» **ممنوع**

## Insight Engine

**Insight** = نکته‌ای که کارفرما احتمالاً ندیده، ولی بعد از خواندن بگوید «درست می‌گه».

### قواعد

1. حداقل **یک** Insight واقعی — اگر نیست، **هیچ Insight مصنوعی ننویس**
2. Insight باید از **تحلیل همین brief** بیاید — نه دانش عمومی کلیشه
3. Insight ≠ ریسک (می‌تواند مرتبط باشد ولی زاویه متفاوت)
4. تست: «آیا کارفرما با خواندن brief خودش به این رسیده؟» — اگر بله، Insight ضعیف است

### نمونه خوب / بد

| بد (مصنوعی) | خوب (واقعی) |
|-------------|-------------|
| «سئو مهمه» | «دسته‌بندی برند/مدل خودرو اگه الان فیکس نشه بعداً ووکامرس رو مجبور می‌کنید دست بزنید» |
| «سرعت سایت مهمه» | «ویروس معمولاً دوبار برمی‌گرده اگه منبع — افزونه کرک — پیدا نشه» |

## ساختار بلوک ۱ — انعطاف‌پذیر

۴–۸ جمله؛ حداکثر ~۱۲ خط. معمولاً شامل:

1. قلاب شخصی (جزئیات brief)
2. درک مسئله
3. رویکرد فنی (ابزار از پروفایل)
4. **یک ریسک مخصوص پروژه** + راه‌حل کوتاه
5. **یک Insight واقعی** (اگر هست — وگرنه حذف)
6. ارجاع به فرم
7. سؤال تخصصی پایانی

**ممنوع در بلوک ۱:** قیمت، زمان، جدول، AI/Cursor، کلیشه (لیست پایین).

## Client Simulation (گیت اصلی — جایگزین امتیاز به‌تنهایی)

بعد از نوشتن بلوک ۱، **نقش کارفرما** را بازی کن:

> «اگر من صاحب این پروژه بودم، آیا حاضر بودم **حداقل یک پیام** برای این فریلنسر بفرستم؟»

| پاسخ | عمل |
|------|-----|
| **بله** | ادامه به امتیازدهی |
| **خیر** | بازنویسی بلوک ۱ — دلیل را مشخص کن (شروع؟ اعتماد؟ ریسک عمومی؟ insight مصنوعی؟ سؤال ضعیف؟) |

### سؤالات کمکی Simulation

1. brief من خوانده شده؟
2. یک نگرانی واقعی من دیده شده؟
3. شبیه ۵۰ پیشنهاد دیگر نیست؟
4. حاضرم یک سؤال جواب بدهم؟
5. فروش اجباری حس می‌کنم؟
6. چیزی برای زیبایی اضافه شده که قابل اثبات نیست؟

**امتیازدهی عددی مکمل است** — Simulation بدون پاسخ «بله» کافی نیست.

## Client Understanding Check (اجباری — قبل Human Review)

**هدف:** نه فقط **حذف ایراد فنی** — کارفرما در **چند ثانیه اول** (۲ جمله اول) باید احساس کند:

> «این فرد **مشکل من** را فهمیده» — نه «یک متخصص فنی پاسخ داده».

**آستانه:** Proposal اولیه قبل از Human Review به سطح **تأیید نهایی** برسد — نه بازنویسی اساسی توسط Human.

**زمان:** بعد از Client Simulation + لایه‌های Intent/Emotional Trust — **قبل** نمایش چک‌لیست Human Review.

### تست اصلی — «چند ثانیه اول»

**فقط ۲ جمله اول** را بخوان (نقش کارفرما):

| پاسخ | عمل |
|------|-----|
| **بله** — حس «فهمیده شدن» | ادامه به ۵ سؤال زیر |
| **خیر** — فنی درست ولی حس «متخصص عمومی» | **بازنویسی** — بدون نمایش به کاربر |

**هر شش سؤال (۰–۵) باید «بله» باشد** — در غیر این صورت **بازنویسی** بلوک ۱.

```markdown
| # | سؤال | ✓/✗ |
|---|------|-----|
| ۰ | **۲ جمله اول:** کارفرما احساس «مشکل من فهمیده شد» می‌کند؟ | |
| ۱ | جمله اول از **مشکل/نگرانی کارفرما** — نه **تکنولوژی** یا **توانایی ما**؟ | |
| ۲ | متن نشان می‌دهد **brief دقیق** خوانده شده؟ | |
| ۳ | **بزرگ‌ترین ریسک ذهنی** کارفرما پوشش داده شده؟ | |
| ۴ | بدون **فرض/تضمین قطعی** قبل از بررسی؟ | |
| ۵ | شخصی‌سازی کافی — نه قالب عمومی برای هر پروژه مشابه؟ | |
```

### اگر «خیر» — اصلاح معمول (بدون Rule جدید)

| سؤال | اصلاح |
|------|--------|
| **۰** | بازنویسی ۲ جمله اول — **نگرانی brief** قبل از روش/ابزار؛ هدف = حس «فهمیده شد» |
| ۱ | شروع از نگرانی انسانی brief — ابزار/افزونه را به جمله دوم یا حذف |
| ۲ | هدف/اصطلاح brief را بازتاب بده (مثلاً CWV، تجربه خرید، امنیت فروشگاه) |
| ۳ | بزرگ‌ترین ترس brief را صریح بگیر (سبد، پرداخت، ظاهر، هزینه پنهان، …) |
| ۴ | «احتمالاً» / «بررسی می‌کنم» — نه «مشکل از X است» یا «حتماً درست می‌شود» |
| ۵ | جزئیات مختص **همین** پروژه — نه قالب عمومی Performance |

### نمونه کیفیت (تحلیل — نه متن ثابت)

**#751682** — نسخه مطلوب پس از HR: شروع «فروشگاه فعال + CWV + تجربه خرید»؛ روش کوتاه؛ بدون WP Rocket در جمله اول؛ بدون تضمین. جزئیات: `proposal-learning.md` → **نمونه کیفیت #751682**.
